# PromptKit UX 优化方案 — 用户主体性 & 共创式命名改造

> 生成时间：2026-07-17 11:1x GMT+8
> 范畴：用户相关命名 / 角色体系 / 审核流话术 / 状态呈现 / 系统文案 → 作用于用户心理的交互体验调整
> 原则：使用者 = 工具的主宰者与共创者，而非「被管理对象」

---

## 一、现状评估：术语审计（已扫描实际代码）

### 问题分级

| 级别 | 现有术语 | 出处 | 心理问题 |
|------|---------|------|---------|
| 🔴 高 | 「用户管理」「添加用户」「停用此用户」 | admin_users.js | 人被物化为"被管理条目"，支配感最强 |
| 🔴 高 | 「观察者」(viewer) | admin_users.js L81 | 旁观者定位，暗示无参与价值 |
| 🔴 高 | 「审核员/批准/驳回」 | asset_library_ui.js L356/523 | 上级裁决式权力语言，打击创作意愿 |
| 🟡 中 | 「审计事件/操作行为/登录会话」 | admin_users.js L193 | 监控感、被追踪感 |
| 🟡 中 | 「编辑员」 | admin_users.js L81 | "员"=雇员/下属暗示 |
| 🟡 中 | 「所有者→审核员→编辑→查看」四级 | asset_library_ui.js | 显性等级链，弱化平等共创 |
| 🟡 中 | 「忙碌/空闲」presence 状态 | presence_client.js | 像考勤系统，不像创作空间 |
| 🟢 低 | 「词卡管理/管理分组/项目管理」 | index.html 导航 | "管理"泛滥，工具味>创作味 |
| ✅ 正面样板 | 「文件管家」「文件管家助手」 | Phase35.3 已定名 | 工具服务于人——这就是正确方向，应全局推广 |

### 结论
系统功能架构无需动；问题集中在**语言框架（Framing）**——现有话术把系统放在支配位（管理/审核/审计/停用），把人放在客体位（用户/观察者/被驳回）。改造成本低（95% 是显示层字符串），心理收益高。

## 二、设计哲学（根本原则 —— 从"管理工具"到"创作伙伴"）

### 核心理念：工具是朋友，是得力助手

> PromptKit 的设计哲学出发点：**应用不是一座牢笼，不是一个控制机器。它是一个理解你的朋友，一个随时待命的得力助手。**

用户打开 PromptKit，不是在进入一个规则体系接受管辖——而是在敲门进入自己的创作书房，而应用是书房里那个熟悉你工作习惯、递工具、提醒遗漏、帮你梳理思路的伙伴。

### 五个根本信条

| # | 信条 | 含义 | 反面（要消灭的） |
|---|------|------|------------------|
| 1 | **创作者是主体** | 一切交互以"我"为出发点：我的词库、我的项目、我邀请的伙伴。应用永远退后一步，站在帮手的位置。 | 「你被分配了角色」「管理员已审核你的提交」——主语是系统的句子 |
| 2 | **分工为创作服务** | 不同职责（主理人/把关人/共创者）是工作室里的自然分工，像导演/摄影/剪辑各司其职，不是科层体系里的上下级。职责差异不意味着人有高低。 | 等级链式角色命名（观察者=底层，所有者=顶层），金银铜视觉暗示 |
| 3 | **反馈是帮助你做得更好** | 「审核」的本质是"伙伴帮你看看这个作品还能怎么打磨"。否定的唯一目的是给出建设性出口——没有出口的否定就是打击。 | 「驳回」（终局否定，无出路） |
| 4 | **透明即尊重** | 系统记录了什么，创作者有权知道且有权查阅。被偷偷监控 → 不信任；被邀请查看自己的足迹 → 被尊重。同一份数据，框架决定感受。 | 内部审计日志不可见，人成了监视客体 |
| 5 | **控制在你手中** | 你自己的在线状态（隐身/专注/在线），由你自己决定是否公开。别人看你是经过你许可的，不是系统替你广播的。 | 自动曝光所有状态，人失去自我呈现权 |

### 一条铁律

> **永远不要让创作者在 PromptKit 里感到自己被监视、被评判、被命令、被分类标签化。每一个按钮、每一个弹窗、每一个 toast 提示，都要传递"我理解你，我帮助你"的信息。**

### 心理学依据

1. **自我决定理论（SDT）**：内在动机三要素 = 自主感 + 胜任感 + 归属感。命名应强化"我发起/我共创/我归属一个团队"。
2. **所有权效应（Endowment Effect）**：「我的词库」比「词卡管理」让人产生资产归属，粘性更高。
3. **框架效应（Framing）**：「驳回」=否定人；「建议打磨」=完善作品。同一动作，创作欲相反。
4. **心理抗拒理论（Reactance）**：被管控感越强，越抗拒使用。「停用此用户」≈ 剥夺自由 → 抗拒；「暂停协作」≈ 关系调节 → 可接受。
5. **正面样板**：「文件管家」「文件管家助手」已证明团队具备"工具服务于人"的直觉，本方案是将其系统化、全应用贯彻。

## 三、核心设计原则（4 条可执行规则）

1. **人是主语**：所有文案以使用者视角构句，系统永远是被省略的助手。
2. **分辨而非等级**：不同角色 = 工作室里的不同分工，用同饱和度不同色相区分，严禁金银铜阶梯色。
3. **否定必有出口**：任何"不通过/不行/不对"必须紧跟着"可以这样做→"的建设性下一步。
4. **显示层改造，数据层不动**：API 字段、DB 枚举全部保留。只改前端术语映射 —— 回归基线 105/105 零风险。

## 四、术语改造映射表

### A. 身份与角色（去支配化）

| 现有 | 建议 | 理由 |
|------|------|------|
| 用户管理 | **团队空间** | 从"管人"到"共处的空间" |
| 用户 | **成员 / 创作者** | 去物化 |
| 添加用户 | **邀请伙伴** | 邀请=平等，添加=录入物品 |
| 管理员 (admin) | **主理人** | 服务与担当，非权力 |
| 所有者 (owner) | **发起人** | 项目由人发起，非占有 |
| 编辑员 (editor) | **共创者** | 核心改造点，直指共创理念 |
| 审核员 (reviewer) | **把关人** | 为品质把关，非裁决他人 |
| 观察者 (viewer) | **鉴赏者** | 观看也是参与，赋予价值感 |
| 停用/启用此用户 | **暂停协作 / 恢复协作** | 针对协作关系，非针对人 |
| 项目成员 | **共创团队** | — |
| 移除成员 | **移出协作** | — |

### B. 审核流 → 共创反馈流（asset_library_ui.js）

| 现有 | 建议 | 理由 |
|------|------|------|
| 草稿 (draft) | **创作中** | 进行时=鼓励继续 |
| 提交审核 (submit) | **邀请反馈** | 主动邀请，非上交待判 |
| 审核中 (in_review) | **共审中** | 大家一起看 |
| ✅ 批准 (approve) | **采纳** | 作品被认可，非权力放行 |
| ❌ 驳回 (reject) | **建议打磨** | 否定作品当前态，不否定人 |
| 已通过 | **已定稿** | 创作语汇 |
| 已驳回 | **待打磨** | 给出下一步方向 |
| 批准意见（可选） | **采纳寄语（可选）** | — |
| 驳回原因（可选） | **打磨建议（建议必填）** | 否定必须附出口 |
| 审核时间线 | **共创记录** | — |

### C. 状态呈现（presence_client.js）

| 现有 | 建议 | 理由 |
|------|------|------|
| 在线 | 在线（保留） | 中性无伤 |
| 空闲 (idle) | **小憩** | 去考勤感 |
| 忙碌 (busy) | **专注中** | busy=打扰属性，专注=创作属性 |
| 离开 (away) | **暂离** | — |
| 局域网在线用户 | **创作现场** | 空间感、氛围感 |

### D. 监控类术语（透明化改造）

| 现有 | 建议 | 说明 |
|------|------|------|
| 审计事件 | 管理端保留「审计事件」(合规需要)；成员自查视图叫 **我的足迹** | 同一数据双视图 |
| 操作行为 | **活动记录** | — |
| 登录会话 | **设备连接** | — |
| 账户活动日志查看器 | **足迹回放** | — |

### E. 泛"管理"导航去味（index.html）

| 现有 | 建议 |
|------|------|
| 词卡管理 | **我的词库** |
| 管理分组 / 管理自定义分组 | **整理分组** |
| 项目管理 | **项目工坊** |
| 项目资产 | **作品资产** |
| 通知中心 | **动态**（可选，低优先） |

### F. 系统文案语气规范

| 场景 | 现有风格 | 新规范 |
|------|---------|--------|
| 成功 toast | "已批准" | "已采纳 ✨"（轻确认+微鼓励） |
| 错误提示 | "加载成员失败" | "没拿到团队名单，稍后再试"（系统担责，不指责人） |
| 空状态 | "选择或创建角色开始编辑"（已不错） | 统一为行动邀请式："从这里开始你的第一个角色 →" |
| 破坏性确认 | "确定永久删除用户「x」？" | **保持严肃明确，不软化**（安全>柔性），仅改措辞："将注销「x」的账户并保留其创作归档，确认？" |

## 五、超越命名的交互调整（8 项）

1. **术语字典中心化**：新建 `frontend/static/js/pk_terms.js`（单一来源 `PK_TERMS = { role: {...}, review: {...}, presence: {...} }`），所有模块从字典取词；未来 A/B 或回退只改一处。与现有 `app_i18n.js` 挂接。
2. **「我的工作台」主权首页**：登录后聚合"我的词库 / 我的项目 / 我的作品 / 我的足迹"，全部以"我的"开头——每天打开工具的第一屏是自己的领地。
3. **自我足迹开放**（P1，需后端小改）：现在审计 admin-only；给每人开放 `GET /api/audit/me`（只能看自己）→ 被记录变成自我掌控。
4. **贡献可视化**：成员卡片展示创作贡献（词卡数/上传数/被采纳数），替代单纯角色标签 → 存在感来自产出而非职级。
5. **角色徽章平权视觉**：四种角色用同饱和度不同色相的徽章（分工），禁用金>银>灰的等级色阶。
6. **反馈流对话化**（P2）：「建议打磨」时必填建议文本，时间线渲染为对话气泡（把关人 ↔ 创作者），而非单向裁决记录。
7. **在场自主权**（P1，需后端小改）：presence 增加「隐身」开关（不广播自己的状态）→ 被看见与否由自己决定。
8. **邀请式入口**：「+ 添加用户」按钮改为「邀请伙伴」，弹窗文案从表单填报式改为"邀请 TA 加入共创"。

## 六、落地分期

### P0 — 纯显示层（0 风险，建议先做，约半天）
- 新建 `pk_terms.js` 术语字典 + 挂接 `app_i18n.js`
- 改 5 个文件的显示映射：`admin_users.js`（roles 字典/按钮/tab 名）、`asset_library_ui.js`（`_st` 状态字典/`roleName`/`actionName`/toast/prompt 文案）、`presence_client.js`（STATES label）、`index.html`（导航/弹窗标题）、`project_roles_ui.js`
- 不动任何 API/DB；`node --check` + 强刷验证

### P1 — 主体性功能（1~2 天）
- `GET /api/audit/me`（复用 audit.py，scope=self）+「我的足迹」前端页
- presence 隐身开关（ws_collab/presence.py 加 opt-out 字段）
- 成员贡献统计（复用现有 stats 聚合）
- 「我的工作台」聚合首页

### P2 — 反馈流重构（2~3 天）
- 打磨建议必填 + 对话式时间线 UI
- 角色徽章视觉平权 + 空状态文案全局巡检

### 不改清单（边界）
- API 字段名、DB 枚举值、`user_audit_log` 表结构 —— 合规与回归基线保护
- 破坏性操作确认弹窗的明确性
- 管理端审计视图专业术语（tooltip 标注新旧对照，过渡期并行）
